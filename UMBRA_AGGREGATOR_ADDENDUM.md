# Umbra Wallet — Addendum: модель агрегатора (без кастодії)

> Продовження UMBRA_BACKEND_SPEC.md. Змінює архітектуру: Umbra НЕ створює й
> НЕ зберігає власні гаманці чи картки користувачів — а прив'язує (linking)
> вже існуючі зовнішні гаманці та картки/банківські рахунки. Umbra виступає
> як брокер з'єднань і UI-шар, не як кастодіан.

---

## 0. Юридична рамка — чесно, без прикрас

Я не юрист і це не юридична консультація, але ось факти, які варто знати
перед тим, як закладати архітектуру:

- **Модель агрегатора дійсно знімає найважчий шар відповідальності** —
  кастодію чужих активів (зберігання приватних ключів чи коштів клієнтів).
  Це головне джерело регуляторних вимог (VASP-ліцензії, страхування,
  резерви) — і його не буде.
- **Але деякі зобов'язання лишаються практично завжди:**
  - Захист персональних даних (GDPR у ЄС, аналогічні норми в Україні —
    ЗУ "Про захист персональних даних").
  - Якщо платформа **фасилітує** обмін крипта↔фіат між користувачами
    (навіть без кастодії) — у частині юрисдикцій (наприклад під MiCA в ЄС)
    це може підпадати під визначення "надання послуг, пов'язаних з
    криптоактивами", навіть якщо ти лише "зводиш" сторони.
  - Договірні відносини з payment/open-banking провайдерами самі вимагають
    від тебе відповідності їхнім комплаєнс-стандартам (вони роблять
    частину AML/KYC роботи за тебе, але вимагають реєстрації як їхній
    клієнт-платформа).
- **Практичний висновок:** архітектура нижче мінімізує технічний і
  фінансовий ризик (ти фізично не можеш вкрасти чи втратити чужі кошти,
  бо не тримаєш їх), але перед публічним запуском з реальними
  користувачами варто **один раз проконсультуватись з юристом**, що
  спеціалізується на fintech/crypto у твоїй юрисдикції — це відносно
  дешево порівняно з ризиком заднім числом.

## 1. Нова архітектура: "linking", не "custody"

```
┌───────────────────────────────────────────────────────────────┐
│                         КЛІЄНТ (Umbra)                          │
│   UI: агрегований дашборд балансів + P2P-матчмейкінг             │
└───────────┬─────────────────────────┬───────────────────────────┘
            │                         │
   ┌────────▼─────────┐     ┌─────────▼──────────┐
   │  Крипто-гаманці    │     │  Банківські картки/  │
   │  (зовнішні)        │     │  рахунки (зовнішні)  │
   │                    │     │                      │
   │  WalletConnect v2  │     │  Open Banking API:    │
   │  → MetaMask,       │     │  Monobank API,        │
   │    Trust Wallet,   │     │  PrivatBank API,      │
   │    Ledger Live,    │     │  Salt Edge / TrueLayer│
   │    Rainbow тощо     │     │  (для інших банків ЄС)│
   └────────────────────┘     └──────────────────────┘
```

**Ключовий принцип:** Umbra ніколи не стоїть "між" грошима/криптою в момент
руху коштів. Лише агрегація стану та ініціація дій у зовнішніх сервісах.

---

## 2. Крипто: WalletConnect + `linked_wallets`

Див. повний текст у репозиторії — таблиця `linked_wallets` зберігає лише
публічні адреси (chain, address, label).

---

## 3. Фіат: Open Banking + `linked_bank_accounts`

Таблиця `linked_bank_accounts` — provider references, без PAN і без
банківських access-токенів у нашій БД.

---

## 4. P2P — чистий посередник

Статуси: `created → awaiting_fiat_payment → fiat_payment_confirmed →
crypto_sent → completed | disputed | cancelled`

Докази: `crypto_tx_hash`, `fiat_payment_reference` — без ескроу на бекенді.

---

## 5–7. Auth, KYC, роадмап

Без змін auth; KYC для P2P лишається рекомендованим. Див.
`UMBRA_BACKEND_SPEC.md` для базового спеку.
